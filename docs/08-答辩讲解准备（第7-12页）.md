## 一、第 7 页：读写一致性，不一致从哪来

### 要讲清的 4 个点

1. **把"不一致"拆成三类可分析的来源**（不是笼统说"缓存和库不一致"）：
   - ① 双写：写库成功、失效缓存失败 → 缓存长期是旧值
   - ② 并发竞态：读-改-写不是原子操作 → 超卖 / 丢失更新
   - ③ 多节点异步复制：主从延迟 → 读到旧数据
2. **五种手段和三类问题是一一对应的**（第 7 页表格），重点说清"手段不是越多越好，是看问题属于哪类"。
3. **本项目一台 MySQL、一个 Redis，没有主从** → ③ 在当前部署下不存在，但要说明"方案五（最终一致 + 兜底）仍然是我们对缓存类数据的基本态度"。
4. **举项目里的真实例子**：①对应 `DishService.evictCache`，②对应 `DishMapper.deductStock` 和 `DeliveryService.grab`。

## 二、第 8 页：方案一 Cache Aside（本项目采用）

### 要讲清的 5 个点

1. **读路径**：查缓存 → 命中直接返回 → 未命中查库 → 回填缓存（带 TTL）。
2. **写路径**：先更新数据库 → **再删除缓存**（不是更新缓存）。
3. **为什么必须"先写库、后删缓存"**：如果先删缓存再写库，删完、库还没写完的窗口里，另一个读请求会把**旧值**重新载入缓存，并一直留到 TTL 过期 —— 这是长期脏数据。反过来最坏只是"短时间内读到旧值"。
4. **为什么是删除而不是更新**：更新缓存要先算出新值；若此时库已被其他事务改动，写进去的就是错值。删除只是让下次读重新加载。
5. **删除失败怎么办**：删除重试（消息队列/本地重试表）、订阅 binlog（Canal）异步删。**我们当前只用 TTL 兜底**，这是可以在答辩里主动说明的取舍。
6. **延迟双删**：删缓存 → 写库 → 延迟 N 毫秒再删一次。项目**没做**，属于演进项，要说清楚不是遗漏而是判断。

### 对应代码

```
DishService.getDetail      第 72~115 行   ← 读：缓存优先 + 回源 + 回填
DishService.saveDish       第 164 行      ← 写：updateById 后 evictCache
DishService.updateStatus   第 189 行      ← 写：updateById 后 evictCache
DishService.updateStock    第 200 行      ← 写：updateById 后 evictCache
DishService.removeDish     第 226 行      ← 写：deleteById 后 evictCache + 榜单失效
DishService.evictCache     第 287 行      ← 只做 delete，不 set
ShopService.getDetail      第 65 行       ← 同样的 Cache Aside，TTL 10 分钟
```

### 一句话记忆

> **读时回填、写后删除；删比改安全，TTL 是最后一道兜底。**

## 三、第 9 页：DishService 代码逐行讲解

### getDetail 的完整流程（要能背下来）

```
1. cacheKey = "cache:dish:detail:" + dishId
2. GET 缓存 → 命中（instanceof Dish）直接返回
3. 未命中 → SETNX lock:dish:cache:{id} "1" EX 5s
   ├─ 抢到锁：
   │    双重检查缓存（等锁期间别人可能已回填）
   │    查库 → 写缓存（TTL = 10 分钟 ± 20% 抖动）→ return
   │    finally：DEL 锁
   └─ 没抢到：
        sleep 50ms → 再读缓存
        仍没有 → 直接查库兜底（不死等，保证可用性）
```

### 三个"为什么"

| 设计 | 为什么 | 被问到时怎么答 |
|---|---|---|
| 互斥锁重建 | 热点 key 过期瞬间并发全打到库 = 缓存击穿 | "20 并发打同一个 key，日志里只会有一条 SELECT" |
| 锁 5 秒过期 | 防止持锁进程崩溃导致死锁 | "finally 正常释放，5 秒是兜底的异常出口" |
| TTL ±20% 抖动 | 固定 TTL 会让同批 key 同时过期 = 缓存雪崩 | "`jitterMinutes(10)`：8~12 分钟之间随机" |

### 现场可以演示的命令

```powershell
# 1. 看缓存与 TTL（抖动后不会是整 10 分钟）
redis-cli TTL cache:dish:detail:DI0000000000000000000000000002

# 2. 删缓存后连续请求同一菜品，观察后端日志只有 1 条 SELECT
redis-cli DEL cache:dish:detail:DI0000000000000000000000000002
```

## 四、第 10 页：方案三~四 + 本项目的取舍

### 要讲清的 4 个点

1. **能用一条原子命令解决，就不要用锁**：
   - 条件更新 `UPDATE ... WHERE stock >= ?`
   - 计数 `INCR / DECR`
   - 多命令原子：Lua 脚本（Redis 内单线程执行）
   - 必须跨多步：`SET NX EX` 分布式锁
2. **方案四（本项目最核心的一条）**：把"绝对不能错"的判断交给磁盘库的原子语义，Redis 只负责降低压力。
3. **方案五**：允许短暂过期 + TTL 收敛 + 关键读回源。我们的一致性目标是"最终一致，窗口 = TTL"，不追求强一致。
4. **本项目的取舍**：方案一 + 方案三 + 方案四，**明确不追求强一致**，而是把不一致窗口压到业务可接受范围。

### 对应代码

| 手段 | 代码 | 说明 |
|---|---|---|
| 分布式锁 | `DeliveryService.java:71` `grab` | `SET NX EX 10s`，value 是 UUID |
| 锁的安全释放 | `DeliveryService.java` `releaseLock` + `UNLOCK_SCRIPT` | Lua：`GET == ARGV[1]` 才 DEL，防误删他人锁 |
| 条件更新 | `DishMapper.java:26` `deductStock` | `WHERE stock >= #{quantity}` |
| Lua 脚本 | `RateLimitInterceptor.java` | 限流：`INCR` + 首次 `EXPIRE`，原子 |
| 库兜底三层 | `OrderService.bindRider` | ①状态必须待取餐 ②`rider_id IS NULL` ③接单上限 |

### 一定要能说的一句

> **锁只负责"减少并发冲突"，正确性由数据库条件兜底；即使 Redis 锁失效，也不会一单多抢。**

## 五、第 11 页：库存不放在 Redis

### 要讲清的 4 个点

1. 库存扣减靠 MySQL 条件更新，判断与扣减在**同一条 SQL** 内完成。
2. **影响行数**是唯一判据：0 → 库存不足；1 → 扣减成功。
3. 对照错误写法：先 `SELECT` 再 `UPDATE`，两个线程可能都读到 1 → 都扣 → 超卖。
4. **为什么这是对的取舍**：Redis 只承担缓存、抢单池、协调职责；即使 Redis 完全宕机，订单与库存的正确性不受影响 —— 只是变慢。

### 对应代码

```java
// DishMapper.java:26
@Update("UPDATE dish SET stock = stock - #{quantity}, update_time = NOW() "
        + "WHERE id = #{dishId} AND deleted = 0 AND stock >= #{quantity}")
int deductStock(@Param("dishId") String dishId, @Param("quantity") int quantity);
```

调用点：`DishService.deductStock(第 248 行附近)`，在下单事务内执行，扣减失败抛异常 → 整单回滚。

### 配套：一张可运行的对照实验

`docs/StockRaceDemo.java` —— 20 线程抢 5 份库存，可对比"先查后改"与"条件更新"的结果。第 18 页会用到。

## 六、第 12 页：一致性方案选型速查表

这一页是"总结页"，**每一行都要能指到代码**：

| 业务场景 | 方案 | 代码位置 | 可以强调的点 |
|---|---|---|---|
| 详情页 / 热点读 | Cache Aside + TTL | `DishService.getDetail`、`ShopService.getDetail` | 写后删缓存 + 击穿防护 |
| 库存扣减 / 秒杀 | 原子条件更新 | `DishMapper.deductStock` | 库存永不为负 |
| 抢单（一单一人） | 分布式锁 + 库兜底 | `DeliveryService.grab` + `OrderService.bindRider` | 锁失效也不一单多抢 |
| 推荐结果 | 缓存 + TTL | `RecommendService`（10 分钟） | 允许过期，重算即可 |
| 会话上下文 | 内存库 + TTL | `ChatbotService`（60 分钟） | 可丢，Redis 为准 |
| **金额 / 余额** | **只落磁盘库 + 事务** | `PaymentService.charge/refund`<br>`StudentMapper.deductBalance/addBalance`<br>`OrderMapper.markRefunded` | **Redis 完全不参与金额** |

### 金额这条要能讲成"三个原子判断"

1. **扣款**：`UPDATE student SET balance = balance - ? WHERE user_id = ? AND balance >= ?` —— 余额不足则影响行数 0，直接回滚整单。
2. **退款闸门**：`UPDATE orders SET pay_status = 2 WHERE id = ? AND pay_status = 1` —— 只有把状态从"已支付"改成"已退款"的那一次才真正退钱，**天然防重复退款**。
3. **流水**：`payment_record` 一单一条，支付 `status=1`、退款 `status=3`，便于对账。

### 高频追问：为什么不把余额放 Redis？

> 余额是"丢了就是资损"的数据。Redis 是内存 + 异步持久化，极端情况下会丢；主从也有延迟。
> 所以金额类一律走 MySQL 事务，Redis 不参与。这也是第 12 页这一行的意思。

## 八、高频追问 10 问（建议背下来）

| # | 问题 | 答法 |
|---|---|---|
| 1 | 为什么先写库后删缓存？反过来呢？ | 先删缓存会在"删完、库没写完"的窗口被回填旧值，长期脏数据；先写库最坏只是短暂旧值 |
| 2 | 删缓存失败怎么办？ | 项目用 TTL 兜底；生产可加重试表或订阅 binlog（Canal）删除 |
| 3 | 延迟双删做了吗？ | 没做。单机 + 短 TTL 下收益有限，属于演进项 |
| 4 | 击穿锁为什么 5 秒？会死锁吗？ | finally 正常释放，5 秒是进程崩溃时的自动兜底 |
| 5 | TTL 抖动会不会频繁回源？ | ±20% 只打散过期时间，命中率略降但避免雪崩 |
| 6 | 库存为什么不放 Redis？ | 判断必须原子且不能丢；条件更新在一条 SQL 内完成，Redis 挂了也不超卖 |
| 7 | 抢单只靠 Redis 锁够吗？ | 不够，锁只减少冲突；正确性由状态校验 + `rider_id IS NULL` + 接单上限兜底 |
| 8 | 锁 value 为什么是 UUID？ | 释放前用 Lua 比对，避免锁过期后被别人拿到时误删他人锁 |
| 9 | 为什么不缓存余额？ | 资损风险最高，Redis 可能丢数据；金额只走 MySQL 事务 |
| 10 | 你们的一致性是强一致吗？ | 不是。缓存类最终一致，窗口 = TTL；金额/库存强一致靠数据库 |
