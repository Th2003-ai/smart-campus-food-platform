## 三、六个演示场景（每个 90 秒，按这个顺序演）

### 场景 1｜热门榜：ZSet 直接排序（对应 PPT 第 15 页）

**操作**：学生窗口点开**「榜单」页**。这一步才会写 Redis；只逛店铺只会写 `cache:shop:detail`，**不会**生成榜单 key。

**敲命令**：
```
ZREVRANGE cache:dish:hot 0 -1 WITHSCORES
TTL cache:dish:hot:list
ZREVRANGE cache:shop:hot 0 -1 WITHSCORES
```

**实测**：4 条菜品，score 就是月销量——现磨豆浆 500、清炒时蔬盖饭 320、番茄鸡蛋盖饭 280、红烧牛肉面 210；店铺榜 1 条。

- `cache:dish:hot` / `cache:shop:hot`：ZSet，**TTL = -1（常驻）**，靠写操作主动失效 + 重启重建
- `cache:dish:hot:list` / `cache:shop:hot:list`：明细快照，**是 String 里存的 JSON**（不是 List 结构），TTL 实测 **240–360 秒**（基准 300，±20% 抖动）

**讲解词**：
> 排序是在 Redis 里完成的，应用层不捞全表、不写 `ORDER BY`。明细 TTL 不是固定 300 秒，而是 300 秒加 ±20% 抖动——这是为了防「大量 key 同一秒集体过期」造成的缓存雪崩。

> ⚠️ 口径提醒：PPT 第 15 页写的是「配套 **List** 缓存实体快照」，代码实际是 **String 序列化的 JSON**。现场说「明细快照」就行，别主动说 List，被追问会露。

---

### 场景 2｜缓存回填与击穿防护（对应 PPT 第 16 页）

**操作**：先删掉某个菜品详情缓存，再点进这个菜品。

```
DEL cache:dish:detail:<菜品ID>        # 先用 KEYS "cache:dish:detail:*" 找到 ID
```

**敲命令**：
```
KEYS "cache:dish:detail:*"
TTL cache:dish:detail:<菜品ID>
TYPE cache:dish:detail:<菜品ID>
```

**实测**：未命中回源后 TTL = **540–660 秒**（10 分钟 ±20% 抖动），`TYPE` 是 `string`；清空缓存后 8 个并发同时打同一菜品，**8/8 全部 200，且只重建了一次**（TTL 只被写一次）。

**讲解词**：
> 缓存刚被清掉的一瞬间，如果 20 个请求同时涌进来，就全部打到 MySQL——这就是击穿。我们的做法是 `SETNX` 抢一把 5 秒的短锁，**只允许一个线程回源重建**，其余线程短等后直接读缓存。

> 补充：`KEYS` 在生产是禁用命令，这里只为演示方便，生产应改用 `SCAN`。这句话主动说出来是加分项。

### 场景 3｜退出登录：Token 黑名单（对应 PPT 第 14 页）

**操作**：学生窗口点「退出登录」。

**敲命令**：
```
KEYS "auth:token:blacklist:*"
TTL auth:token:blacklist:<那个 token>
```

**实测**：退出后黑名单里出现该 token，TTL = **43067 / 42879 / 42741** 量级（≈ 12 小时，等于 token 剩余有效期）；用旧 token 再访问 `/orders` → `code=401 未登录或登录已过期`。

**讲解词**：
> JWT 是无状态的，签发之后服务端本来管不着它。所以退出登录时把 token 写进 Redis 黑名单，拦截器每次请求先查一次。TTL 特意设成「token 剩余有效期」——token 自然过期后，黑名单条目也正好自动消失，不需要任何定时清理任务。

**加分动作**：退出后按浏览器后退键再访问受保护页面，接口返回 401，日志里有「Token 已在黑名单中」。

### 场景 4｜骑手在线状态：用 TTL 表达离线（对应 PPT 第 17 页）

**操作**：骑手窗口打开页面（WebSocket 建立即标记在线），或直接点一下刷新。

**敲命令**：
```
KEYS "rider:online:*"
TTL rider:online:<骑手ID>
GET rider:online:<骑手ID>
```

**实测**：`heartbeat` 后出现 `rider:online:R000000000000000000000000000001`，**TTL = 60**，value 是最后心跳的毫秒时间戳。

**讲解词**：
> 骑手进程崩溃或断网时，**不会主动上报下线**。所以这里不存「在线/离线」布尔值，而是存最后一次心跳的时间戳，60 秒过期即视为离线——**让 TTL 承担离线判定**，不需要任何定时扫描任务。

### 场景 5｜抢单：分布式锁 + 抢单池（对应 PPT 第 19 页，最出彩的一个）

**完整顺序**（三个窗口配合）：

| 步骤 | 窗口 | 动作 |
|---|---|---|
| 1 | 学生 | 下单，**配送方式选「骑手配送」** |
| 2 | 商户 | 订单页出现新单 → 点「接单」 |
| 3 | 商户 | 点「出餐」（生成取餐码） |
| 4 | 骑手 | 抢单大厅出现该单 → 点**一次**「抢单」 |

**敲命令**（第 3 步出餐后、第 4 步抢单前敲）：
```
ZRANGE delivery:grab:pool 0 -1 WITHSCORES
KEYS "lock:order:grab:*"
```

**实测**：出餐后抢单池出现该订单，score = 出餐时间戳（保证「先出餐先被看到」）；骑手大厅可用单数 1；抢单成功后池中该单被移除、锁随即释放；第二次点抢单返回 `40002 手慢了，订单已被其他骑手抢走`。

> ⚠️ **只点一次抢单。** 第二次虽然会正确报「手慢了」，但代码在抢单失败分支里会把该订单**重新写回抢单池**（本意是「被锁期间别人也抢不到」）。于是 `ZRANGE delivery:grab:pool` 里会留下一单已经完成的「幽灵记录」，大屏上会有点尴尬。要现场演示「抢不到」，用第二个骑手账号，别用同一个人连点。

**讲解词**：
> 锁只是「减少并发冲突」，真正保证一单只能一人抢的是数据库的条件更新（`WHERE rider_id IS NULL` 加上乐观锁 version）。**即使 Redis 整台挂掉，也不会出现一单多抢**——只是会慢一点、并发差一点。这就是「Redis 做加速，MySQL 做正确」的分工。

### 场景 6｜订单超时自动取消：ZSet 延时队列（PPT 未含此页，可作为加分补充）

**这页 PPT 里没有**，但代码里有，讲完场景 5 顺口提一句会很加分。

**操作**（改为 1 分钟，便于现场看到效果）：

```sql
UPDATE sys_config SET config_value = '1' WHERE config_key = 'order.auto.cancel.minutes';
```

> ⚠️ **配置有 60 秒本地缓存**，改完要**等够 60 秒**（或重启后端）下单才按 1 分钟算。

1. 学生下一单，**不要**去商户端点接单
2. 等约 65 秒（到截止时间）
3. 管理员窗口触发 `POST /api/admin/orders/sweep-timeout`（或等定时任务，最多再晚 60 秒）
4. 订单变为「已取消」，库存回补

**敲命令**：
```
ZRANGE order:timeout:queue 0 -1 WITHSCORES
```

**实测**：下单后队列里 `member = 订单ID`、`score = 到期毫秒时间戳`；1 分钟后被取消，`cancelReason = 超时 1 分钟未接单，系统自动取消`，队列中该单同时消失。

**讲解词**：
> 下单时把订单号 `ZADD` 进队列，score 是「到期时间戳」。定时任务每 60 秒 `ZRANGEBYSCORE 0 now` 取出所有到期订单。用 `ZREM` 的返回值做抢占——只有删除成功的那个实例才处理，多实例部署天然不会重复取消。没有为每一单起一个定时器，因为定时器在应用重启后就丢了。

**演示完记得改回去**：
```sql
UPDATE sys_config SET config_value = '15' WHERE config_key = 'order.auto.cancel.minutes';
```

## 五、redis-cli 速查卡（可打印贴屏幕）

| 想看什么 | 命令 |
|---|---|
| 全部 key（小库） | `KEYS *` |
| 某类 key | `KEYS "cache:dish:*"` |
| 热门菜品榜 | `ZREVRANGE cache:dish:hot 0 -1 WITHSCORES` |
| 热门店铺榜 | `ZREVRANGE cache:shop:hot 0 -1 WITHSCORES` |
| 抢单池 | `ZRANGE delivery:grab:pool 0 -1 WITHSCORES` |
| 某单在池里的分数 | `ZSCORE delivery:grab:pool <orderId>` |
| 超时队列 | `ZRANGE order:timeout:queue 0 -1 WITHSCORES` |
| 黑名单 | `KEYS "auth:token:blacklist:*"` |
| 骑手在线 | `KEYS "rider:online:*"` → `TTL rider:online:<id>` |
| 剩余有效期 | `TTL <key>`（-1 = 常驻，-2 = 不存在） |
| key 类型 | `TYPE <key>` |
| 实时看命令流（演示抢单时很有用） | `MONITOR` |
| 清空（演示前） | `FLUSHDB` |

> `MONITOR` 是演示「锁」的最好工具：抢单时把 MONITOR 开着，大屏上能直接看到 `SET lock:order:grab:... NX EX 10` 和随后的 `DEL`。

## 七、预判提问（8 问，提前对好答案）

| 提问 | 回答要点 |
|---|---|
| 为什么库存不放在 Redis 里扣？ | 库存扣减靠 MySQL `UPDATE ... WHERE stock >= n` 条件更新，判断和扣减在同一条 SQL 里完成，中间没有窗口。Redis 只做加速。 |
| 缓存和数据库不一致怎么办？ | 先写库、再删缓存（不是更新缓存）；删失败有重试/兜底；还可以延迟双删、订阅 binlog。 |
| Redis 单线程为什么还快？ | 纯内存、无锁竞争、IO 多路复用；真正的瓶颈是大 key 和慢命令。 |
| 两个后端实例，WebSocket 推送怎么不串？ | 目前是进程内广播，跨实例靠商户订单页 5 秒轮询兜底；规模大了要换成 Redis Pub/Sub 或 MQ。这是已知缺口，主动承认更可信。 |
| 四个窗口为什么登录不串？ | `localStorage` 按 origin（协议+主机+端口）隔离，四个端口就是四个 origin。 |
| 超时队列为什么用 ZSet 不用定时器？ | 定时器重启就丢，ZSet 持久化；一次 `ZRANGEBYSCORE` 取全部到期单，O(log N)；`ZREM` 返回值天然做多实例抢占。 |
| 为什么超时演示要等一分多钟？ | 扫描周期 60 秒 + 配置有 60 秒缓存，这两个都是刻意的取舍。 |
| 项目里 Redis 到底是缓存还是数据库？ | 两种身份都用到了：详情缓存是缓存；抢单池、在线状态、超时队列是当内存数据库用。 |

这一节是**真跑一遍**的结果，不是设计推演。演示前如果数字对不上，说明是环境问题，不是代码问题。

| 场景 | 实测结果 |
|---|---|

**预演同时发现的两个代码问题**（不影响演示，但可以顺手修）：

1. **抢单失败会把订单写回抢单池**（`DeliveryService.grab` 的失败分支）：已经被别人抢走的单会留下「幽灵 member」，`ZRANGE delivery:grab:pool` 能看到已完成订单。修法：只在「锁被占用 / 业务异常但订单仍未分配」时回池。
2. **PPT 第 15 页写「List 缓存」，代码实际是 String 序列化 JSON**：讲的时候按「明细快照」说，或改一下 PPT 措辞。
